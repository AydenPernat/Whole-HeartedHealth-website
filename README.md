# Whole-Hearted Health

An Express server with the original pink-and-gold site, a shop, events, verified accounts, a customer portal, support requests, newsletters, and owner administration.

## Run locally

From this repository root:

```sh
npm --prefix Whole-HeartedHealth-website-main ci
npm start
npm test
```

Visit http://localhost:3000. Copy the application `.env.example` to `.env` for private configuration. Without a mail provider, local development prints verification links to the terminal. Production refuses to simulate delivery. Never share logs containing recovery links.

## Render deployment

Render is configured manually. Use root directory `Whole-HeartedHealth-website-main`, build command `npm ci`, start command `npm start`, and health check `/healthz`. Connect PostgreSQL through `DATABASE_URL` and persistent upload storage through `UPLOADS_PATH` (for example `/var/data/uploads` on a disk mounted at `/var/data`). Removing the YAML file does not remove an existing Render service.

Set the prompted secrets in Render:

- `ADMIN_EMAIL`: your owner sign-in email and support-notification recipient.
- `ADMIN_PASSWORD`: a unique long owner password. The owner is configured on the server, not through public registration or password recovery.
- `PUBLIC_BASE_URL`: your final HTTPS website origin, without a trailing slash. Use the Render service URL until the custom domain works, then update it.
- `RESEND_API_KEY`: a sending key from your Resend account.
- `EMAIL_FROM`: `Whole-Hearted Health <hello@YOUR-VERIFIED-DOMAIN>`.
- `BACKUP_SECRET`: generated by Render. Keep a separate secure copy: old backups need the same key.

Set `DATABASE_URL` and `UPLOADS_PATH` in Render. Use one web-service instance with the attached disk. Database updates lock the shared state row and commit before success responses; this is a deliberately simple small-site store, not a high-throughput commerce database. Large newsletter sends block other API work while they run. Use a queued email worker before growing to large campaigns.

Check `/healthz` after deploying. Sign in as owner, add real products/images and real upcoming events, and verify a customer account using a real inbox. The supplied seed catalog is empty; unused demo products and events have been removed. Existing PostgreSQL data is preserved on deployment.

## Porkbun custom domain

In Render, open the service's Settings → Custom Domains and add your Whole-Hearted Health domain. In Porkbun's DNS editor, enter the exact host, type, and target shown by Render. Remove only conflicting website records; keep existing email records. Return to Render and verify the domain, then update `PUBLIC_BASE_URL`. Render manages HTTPS certificates. Crimson Creations was only a feature reference; its domain is not configured for this site.

Official instructions: https://render.com/docs/custom-domains

## Resend email setup

Create a Resend account, add a domain or sending subdomain you own, and copy Resend's displayed DNS verification records into Porkbun. Wait until Resend reports the domain verified. Create a sending API key and enter it in Render with the matching `EMAIL_FROM`. Website DNS and email verification records serve different purposes; both can coexist.

Test registration, resend verification, password recovery, support notifications, newsletter confirmation, and unsubscribe using an inbox you control. Email provider acceptance is not proof of inbox delivery; review the Resend delivery log. No live email was sent during development testing.

Official instructions: https://resend.com/docs/dashboard/domains/introduction
API reference: https://resend.com/docs/api-reference/emails/send-email

## Features and intentional scope

- Verified registration, resend verification, sign-in/out, expiring one-time password resets, and hashed passwords.
- Customer portal with order progress and support-request notes. Notes appear in the portal; they do not send automatic update emails.
- Product/event creation, editing, removal; order/request management; account and subscriber search.
- Confirmed newsletter subscriptions, token-based unsubscribe links, and removal through account settings.
- Owner-only admin role changes, account deletion, encrypted data backups, preview, and restore. Restore clears sessions and recovery tokens.
- Request throttling, same-origin write checks, HttpOnly session cookies, and public-file allowlisting.

Project ratings/comments and project-request workflows from Crimson Creations were not copied: this remains a wellness shop with orders and support requests. There are no fabricated reviews, sample clothing listings, fake app downloads, or pretend social links. Add accurate product content and confirm your business contact and policy details before launch.

## Optional Stripe checkout

Checkout is paused by default. Set `CHECKOUT_ENABLED=true`, `STRIPE_SECRET_KEY`, and `STRIPE_WEBHOOK_SECRET` in Render to enable it. Set `CHECKOUT_ENABLED=false` to pause new checkout sessions again. Apply the environment change and let the service restart. Products, carts, and existing orders stay accessible. Configure a Stripe webhook at `/api/stripe/webhook` for `checkout.session.completed` and `checkout.session.async_payment_succeeded`. Verify shipping and tax settings for your business before taking orders. Prices come from the server; payment details are collected by Stripe.

## Backups and verification

Owner downloads are manual and include database content only, **not uploaded image files**. Back up the persistent image disk separately. Keep backups and the encryption key private. Restore overwrites current database content and signs everyone out.

`npm test` exercises verification, rejected/unverified sign-ins, token reuse prevention, recovery/session invalidation, authorization, product edits, newsletters, unsubscribe authorization, encrypted restore, private-file protection, cross-origin rejection, and Stripe price/webhook handling with mocked external delivery/payment services. A separate mocked PostgreSQL test checks commit ordering, concurrent writes, and commit-failure recovery. Real PostgreSQL and live provider deployment must also be validated in Render; local tests do not substitute for that.

The privacy and terms pages describe the implemented service. Confirm business-specific fulfillment, return, and privacy requirements before launch. Dependency audit after compatible updates: zero reported vulnerabilities.

## Files to keep

- Root `package.json`: convenience commands to start and test the application from the outer folder.
- Application `package.json` and `package-lock.json`: dependencies and reproducible installation.
- `server.js`, frontend files, and referenced images: the running website.
- `data.json`: local development storage and the initial database seed. Do not delete it to reset a live site.
- `.env` (private), `.env.example`, and root `.gitignore`: configuration and secret exclusion.
- Test files: checks for account, checkout, and storage behavior.
- `uploads/`: any images added through administration; keep these backed up.

The old blog, tracking, and individual sample-event URLs redirect to the current events page or customer portal. Their duplicate HTML files are no longer needed. `node_modules/` can be recreated with `npm ci`, but is kept locally so the server continues working and is excluded from Git.

## Frontend maintenance

The stylesheet retains the pink-and-gold theme and hero bubbles. Obsolete coupon, payment-modal, banner, blog, app-download, social-rail, and intro-splash rules were removed. Navigation uses one fullscreen menu at all widths. Use the Node server (`npm start` on port 3000), rather than Live Server, to test redirects and account features.

The navigation tests cover all public pages and their local asset references, five legacy redirects, and safe post-login destinations. Browser checks also cover phone layouts, the product gallery, add-to-cart, wishlist login return, sign-out, and the admin layout using isolated temporary data.

## Administration

Sign in with the owner email/password configured as `ADMIN_EMAIL` and `ADMIN_PASSWORD`, then open `/admin.html`. There are no typed admin commands or public admin codes. Use the dashboard to manage products, events, orders, support requests, and newsletters. The owner can also promote verified accounts, remove administrators, delete accounts, and download/preview/restore encrypted backups. Checkout availability is controlled by the `CHECKOUT_ENABLED` environment setting above.

## Hamburger menu settings

Open `admin.html` and use the **Hamburger menu** editor to show or hide each link, choose its audience, switch between text and its icon, and move it up or down. The preview can show a visitor, signed-in customer, or administrator view. Click **Save menu** to apply changes across the website; **Reset to defaults** stages the default menu until saved.

Hidden items occupy no menu space. Visibility controls menu links. Shop is the exception: hiding Shop, or limiting its audience, also hides shop links and collection sections for the affected visitors across the site. Direct page URLs and existing account/admin access rules remain unchanged. The administration item is always restricted to administrators. Settings are kept in the same local or PostgreSQL state as the rest of the site and are included in encrypted backups.

## Clean page URLs and newsletter links

Pages use extensionless URLs such as `/shop`, `/signin` and `/profile`. Existing `.html` links redirect permanently while preserving query parameters, including verification, recovery, payment and unsubscribe tokens. Deploy the updated server, frontend scripts and HTML pages together.

Newsletter emails include an HTML footer whose clickable text is **Unsubscribe**, plus a plain-text fallback for email clients that cannot display HTML. Newsletter message content is escaped before insertion into HTML.

For local preview, use an empty `DATABASE_URL` (JSON storage) and `PUBLIC_BASE_URL=http://localhost:3000`. Render internal database hostnames only resolve inside Render; use its external URL and appropriate SSL settings if intentionally connecting from outside Render. Explicit environment settings, including an empty database URL, take precedence over `.env`.
